# Requirements Document: Tenant Subscription Billing & Flutterwave Integration

## Module: Tenant Subscription Billing & Payments

### Subsystem: TallyBakery Multi-Tenant Operations Platform

---

## Introduction

TallyBakery is an offline-first multi-tenant operations, inventory, and shift reconciliation SaaS platform for shift-based businesses, with commercial bakeries as the primary reference implementation.

To support SaaS commercialization and sustainable operations, TallyBakery requires an automated, resilient subscription billing engine. This engine enables bakery owners (Super Admins / Organization Owners) to select subscription tiers, initiate self-serve checkout, renew recurring billing plans, and maintain uninterrupted operational access across their branches and departments.

Subscription billing for TallyBakery is powered by the **Flutterwave API** (supporting cards, bank transfers, mobile money, and automated payment plans across African and international markets). The billing system must guarantee multi-tenant isolation, tamper-evident audit trails, deterministic idempotency, zero-trust server-side transaction verification, and secure, high-throughput webhook handling.

---

## Existing Capabilities and Boundaries

- **Existing Capabilities**:
  - `tenants` schema (`apps/api/src/database/schema/tenancy.schema.ts`) already maintains `subscriptionTier` (`varchar(50)`), `subscriptionStatus` (`varchar(50)`), and `defaultCurrency` (`varchar(3)`).
  - Multi-tenant boundary isolation enforced through `TenantScopeGuard` and `SessionGuard`.
  - Immutable role ceilings and fine-grained permissions vocabulary (`VALID_PERMISSIONS`).
  - Immutable append-only audit event logging via `AuditService` and `audit_events` schema.
  - Idempotency table (`idempotency_records`) with request fingerprinting.
  - Shared contracts and error codes (`@repo/shared`).

- **Boundaries & Out of Scope**:
  - **In Scope**:
    - Multi-tier billing plan catalog (`STARTER`, `GROWTH`, `ENTERPRISE`).
    - Flutterwave Standard Hosted Checkout session creation (`POST /payments`).
    - Server-side transaction verification (`GET /transactions/{id}/verify`).
    - Webhook ingestion endpoint (`POST /webhooks/flutterwave`) with constant-time `verif-hash` header signature verification.
    - Tenant subscription lifecycle state transitions (`TRIALING`, `ACTIVE`, `PAST_DUE`, `SUSPENDED`, `CANCELED`).
    - Subscription invoice history and audit events.
    - Grace periods (7 days) for failed renewals before operational write suspension.
  - **Out of Scope**:
    - Direct credit card PAN collection on TallyBakery servers (PCI-DSS out-of-scope; all card handling uses Flutterwave hosted modal or hosted payment links).
    - Customer POS checkout / retail order payments (Module 6 handles customer order payments separately).
    - Arbitrary per-seat micro-billing (plans are flat-rate or tiered per tenant/branch limits).

## Glossary

- **Tenant**: An isolated organizational account representing a commercial bakery business.
- **Subscription Plan**: A predefined billing package defining price, currency, interval (`MONTHLY`, `YEARLY`), tier, and feature/branch limits.
- **Subscription**: A tenant's active contractual billing association with a plan, capturing current period start/end, status, and Flutterwave customer/subscription tokens.
- **Flutterwave Checkout**: Flutterwave hosted payment rail generating a secure checkout redirect URL for multi-channel collection (cards, NIP bank transfers, mobile money).
- **tx_ref**: A deterministic, unique transaction reference string generated by TallyBakery in the format `SUB-{tenantId}-{planCode}-{timestamp}`.
- **verif-hash**: Flutterwave's secret HMAC/hash header passed in webhook POST requests for source verification.
- **Grace Period**: A 7-day window following renewal payment failure during which operational access is maintained while warning banners are surfaced.
- **Tenant Suspension**: Soft restriction of tenant write operations when an account is past due beyond the grace period.

## Requirements

### Requirement 1: Subscription Plan Catalog & Quotas ([SUB-01])

**User Story:** As a bakery owner, I want to view clear subscription plan options (Starter, Growth, Enterprise) with pricing and branch allowances so that I can choose the appropriate plan for my business.

#### Acceptance Criteria

1. THE System SHALL maintain an authoritative catalog of subscription plans including `code`, `name`, `tier`, `priceAmount`, `currency`, `interval` (`MONTHLY` | `YEARLY`), `maxBranches`, `maxStaff`, and `active` status.
2. WHEN an authenticated tenant owner with permission `subscription:read` requests available plans (`GET /subscriptions/plans`), THE System SHALL return all active plans matching the tenant's default currency or system default currency.
3. THE System SHALL prevent non-owner staff roles from accessing subscription pricing management.

---

### Requirement 2: Flutterwave Hosted Checkout Initiation ([SUB-02])

**User Story:** As a bakery owner, I want to select a plan and receive a secure checkout link so that I can pay using my preferred payment method (Card, Bank Transfer, Mobile Money).

#### Acceptance Criteria

1. WHEN an authenticated owner with `subscription:manage` initiates checkout (`POST /subscriptions/checkout`) with a valid `planId`, THE System SHALL create a pending `subscription_invoices` record and generate a unique, collision-proof `tx_ref` (`SUB-{tenantId}-{planCode}-{timestamp}`).
2. THE System SHALL invoke the Flutterwave Hosted Checkout API (`POST /payments`) passing `tx_ref`, `amount`, `currency`, `redirect_url`, customer details (owner name and email), and metadata (`tenantId`, `planId`).
3. THE System SHALL return the Flutterwave checkout URL (`paymentLink`) and `tx_ref` to the client.
4. IF Flutterwave API is unreachable or returns an error, THEN THE System SHALL return a standardized `DEPENDENCY_UNAVAILABLE` error and log the diagnostic details without corrupting tenant state.

---

### Requirement 3: Mandatory Server-Side Transaction Verification ([SUB-03])

**User Story:** As the system architect, I want every completed payment to be verified server-side with Flutterwave before updating subscription status, so that client tampering or spoofed redirect URLs cannot grant unauthorized access.

#### Acceptance Criteria

1. WHEN a client redirects back to TallyBakery or requests payment verification (`GET /subscriptions/verify?transaction_id={id}&tx_ref={tx_ref}`), THE System SHALL query Flutterwave's transaction verification endpoint (`GET /transactions/{id}/verify`).
2. THE System SHALL verify that the transaction status is `"successful"`, the currency matches the expected plan currency, the amount is greater than or equal to the invoice amount, and the returned `tx_ref` exactly matches the local invoice record.
3. IF the verification passes, THE System SHALL atomically:
   - Transition the invoice status to `PAID`.
   - Update the tenant's `subscriptionTier` and `subscriptionStatus` to `ACTIVE`.
   - Record the `currentPeriodStart` and `currentPeriodEnd` (calculated based on plan interval).
   - Record payment card token / customer ID for recurring renewals where provided by Flutterwave.
   - Emit an audit event `TENANT_SUBSCRIPTION_ACTIVATED`.
4. IF Flutterwave verification reports `failed` or amount/currency mismatch, THEN THE System SHALL mark the invoice as `FAILED`, reject activation, and log an audit security warning.

---

### Requirement 4: High-Reliability Secure Webhook Ingestion ([SUB-04])

**User Story:** As the system administrator, I want automated recurring charges, cancellations, and renewals processed asynchronously via webhooks so that tenant access remains accurately synchronized without manual intervention.

#### Acceptance Criteria

1. WHEN Flutterwave sends a webhook event (`POST /webhooks/flutterwave`), THE System SHALL validate the `verif-hash` HTTP header against the configured secret webhook hash (`FLW_WEBHOOK_HASH`) using constant-time comparison (`crypto.timingSafeEqual`).
2. IF the `verif-hash` header is missing, invalid, or mismatched, THEN THE System SHALL reject the request with HTTP `403 Forbidden` and record a security incident.
3. THE System SHALL respond to valid Flutterwave webhook requests with HTTP `200 OK` within 5 seconds to comply with the 60-second provider SLA.
4. THE System SHALL record incoming webhook payloads in a deduplicated `payment_webhook_events` table using the provider's `event_id` or transaction reference to guarantee idempotent, exactly-once processing.
5. WHEN a `charge.completed` webhook event is processed for an existing subscription, THE System SHALL verify the transaction and renew the tenant's `currentPeriodEnd`.
6. WHEN a `subscription.cancelled` or renewal charge failure event is received, THE System SHALL transition the tenant status to `PAST_DUE` and trigger a grace period timer.

---

### Requirement 5: Subscription Lifecycle State Machine & Grace Period ([SUB-05])

**User Story:** As a bakery owner, I want a grace period when a card renewal fails so that my bakery's daily shifts, bread baking, and dispatch operations are not abruptly halted.

#### Acceptance Criteria

1. THE System SHALL maintain the following deterministic subscription state transitions:
   - `TRIALING` -> `ACTIVE` (upon successful initial payment)
   - `ACTIVE` -> `PAST_DUE` (upon renewal charge failure or billing expiration)
   - `PAST_DUE` -> `ACTIVE` (upon successful recovery payment within grace period)
   - `PAST_DUE` -> `SUSPENDED` (upon expiration of the 7-day grace period)
   - `ACTIVE` | `PAST_DUE` -> `CANCELED` (upon explicit owner cancellation at period end)
2. WHILE a tenant is in `PAST_DUE` within the 7-day grace period, THE System SHALL permit normal operational writes while displaying an executive warning banner to managers and owners.
3. WHEN the 7-day grace period expires with no successful payment, THE System SHALL transition the tenant's `subscriptionStatus` to `SUSPENDED` and update the tenant record status to `SUSPENDED`.
4. WHILE a tenant is `SUSPENDED`, THE System SHALL reject all operational mutations (creating orders, recording batches, sealing shifts, updating inventory) via `TenantScopeGuard` with error code `ACTIVE_TENANT_REQUIRED` while allowing owners to access subscription recovery billing.

---

### Requirement 6: Access Control & Role Ceiling Enforcement ([SUB-06])

**User Story:** As an organization owner, I want subscription management strictly restricted to the `OWNER` role so that subordinate managers or cashiers cannot view billing details or cancel subscriptions.

#### Acceptance Criteria

1. THE System SHALL define two distinct permissions in `VALID_PERMISSIONS`:
   - `subscription:read`: View current subscription plan, status, renewal dates, and invoice history.
   - `subscription:manage`: Initiate checkout, change plans, update billing details, and cancel subscriptions.
2. THE System SHALL place `subscription:read` and `subscription:manage` exclusively within the system `OWNER` role ceiling in `ROLE_CEILINGS`.
3. THE System SHALL prohibit assigning `subscription:manage` to non-owner dynamic roles.
4. IF a non-owner actor attempts to access `/subscriptions/checkout` or `/subscriptions/cancel`, THEN THE System SHALL reject the request with HTTP `403 Forbidden` (`SCOPE_FORBIDDEN`).

---

### Requirement 7: Invoicing, Payment History & Receipts ([SUB-07])

**User Story:** As a bakery owner, I want access to downloadable receipts and invoice history so that I can maintain accurate accounting records for my business expenses.

#### Acceptance Criteria

1. THE System SHALL record an immutable record in `subscription_invoices` for every charge attempt, capturing `invoiceNumber`, `amount`, `currency`, `status`, `paymentMethod`, `flwRef`, `txRef`, and `paidAt`.
2. WHEN an owner requests billing history (`GET /subscriptions/invoices`), THE System SHALL return a paginated list of historical invoices ordered by creation date descending.
3. THE System SHALL support fetching individual invoice receipt details (`GET /subscriptions/invoices/:id`).
